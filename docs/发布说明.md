# 发布说明

面向维护者的发布流程与验收清单。只做发布的人看这一份就够。

## 版本号只有一个来源

`main.go` 里的 `var Version = "0.2.0"`。任何地方都不要另写版本字面量：

- 自动更新拿它和 GitHub 最新 release 的 `tag_name` 比较；
- 前端「关于」页读的是 `app.PSStatus.Version`（PS 版本）和这个 `Version`（程序版本）；
- CI 打出来的 exe 文件名不带版本号，版本靠 release tag 区分。

发版时三处必须一起改：

1. `main.go` 的 `var Version`
2. `CHANGELOG.md` 新增一节（`## vX.Y.Z — YYYY-MM-DD`）
3. git tag（`vX.Y.Z`，带 `v` 前缀）

## 发布前验收清单

在 `E:\套图程序-go\app` 依次跑，全绿才发：

```bash
go build ./...
go vet ./...
go test ./... -count=1
```

再手工确认三件事：

1. **能力矩阵**：`go run` 打印 `psx.For("27.7.0")`，`Verified` 必须是 `true`，
   `DoJavaScript` / `NoDialogs` / `EditSmartObject` 三项必须为 `true`，`ReplaceContents` 必须为 `false`。
2. **端到端**：`go run ./cmd/probe` 跑一次真实套图。它不经过 GUI，路径硬编码在源码里，
   产物落在 `E:\Temp\out\go-probe`。看它输出的 `OK <字节数> <路径>` 行数是否等于模板格数。
3. **前端**：`wails dev` 起来后逐页点一遍（套图 / 任务队列 / 成品 / 设置 / 关于），
   确认没有报错。**先走浏览器端口审查，最后才打包 exe**，不要靠反复操控桌面 GUI 验收。

## 打包

```bash
cd frontend && pnpm install && pnpm run build
cd .. && wails build -platform windows/amd64 -trimpath
```

产物：`build/bin/套图工作台.exe`（单文件，约 12MB）。

`build/bin/config.json` 是运行时生成的本地配置，**含用户 API Key，已在 `.gitignore` 里排除**，
不要手工加进仓库。

## 发布到 GitHub

走 `github-auto-publisher` skill 的两阶段流程，不要裸 `git push`：

```bash
python ~/.agents/skills/github-auto-publisher/scripts/publish.py plan \
  --repo "E:/套图程序-go/app" --remote origin --branch main \
  --message "release: v0.2.0" \
  --version-file main.go \
  --include main.go --include CHANGELOG.md \
  --check-json '["go","test","./...","-count=1"]'
```

`plan` 返回 `status: ready` 后再跑同一条命令的 `publish`。

skill 的硬性前提（踩过就知道多容易漏）：

- 本地 `git config user.name` 必须等于 `user.email` 里 `@users.noreply.github.com` 前的 handle
  （本项目是 `z2476720314-sys` / `z2476720314-sys@users.noreply.github.com`）；
- remote 必须是 github.com 的 **https** 地址；
- **远端分支必须已存在**，且远端 SHA == 本地 HEAD（首次建仓要先手动建立 main 基线）；
- `--version-file` 必须同时在 `--include` 里，且必须真的改了；
- 不能有 release hooks、不能是 detached HEAD、index 必须干净。

## 打 tag 与建 release

推送成功后：

```bash
git tag -a v0.2.0 -m "v0.2.0"
git push origin v0.2.0
gh release create v0.2.0 -R z2476720314-sys/titao-workbench \
  --title "套图工作台 v0.2.0" --notes-file CHANGELOG.md
```

推 tag 会自动触发 `.github/workflows/release.yml`：先 `verify`（build/vet/test），
再 `build`（wails 打包），算 SHA-256，然后挂到 release 上。
如果 CI 构建失败，release 会是空的 —— 手动 `gh release upload` 本地 exe 兜底。

## 自动更新怎么工作

用户在「设置」里勾上 `update_check`（默认开）时，程序启动后会：

1. `updater.CheckLatest(ctx)` 查 `https://api.github.com/repos/z2476720314-sys/titao-workbench/releases/latest`；
2. `updater.IsNewer(当前版本, tag_name)` 判断有没有更新；
3. 有则 `updater.Download` 下载 exe、`updater.VerifySHA256` 比对同 release 的 `.sha256` 附件；
4. `updater.ApplyReplace` 生成 `titao-update.bat` 并启动它，脚本等主进程退出后 `copy /y` 覆盖再拉起新版本。

**全程静默失败**：网络不通、被限流（403/429）、仓库 404、预发布/草稿，都只返回 error
不打断用户。`prerelease` 和 `draft` 永远不会被当作更新目标。

替换脚本不结束进程、不删用户数据，只重试 `copy /y` 最多 60 次（每次间隔约 1 秒）；
60 次仍失败就打印「更新失败：无法覆盖 …，请手动替换。」并 `pause`，不会把程序搞成打不开的状态。

## 版本兼容

`internal/psx/capability.go` 的 `For(version)` 按 PS 大版本判定能力：

| PS 大版本 | Verified | 说明 |
|---|---|---|
| 27（2025） | ✅ | 实测通过，本项目主目标 |
| 13–26 | — | 保守放行，标注「未实测」 |
| < 13（CS6 之前） | — | 缺 `placedLayerEditContents`，套图功能不可用，报错提示升级 |
| 未知 / 空 | — | 保守放行，标注「版本未知」 |

`ReplaceContents` 在任何版本都是 `false`。实测 `placedLayerReplaceContents` 会把智能对象
原有透视变换从 271×601 放大成 1331×3211，成品完全错位，所以本项目永远走
`placedLayerEditContents` 进内部文档替换这条路。
