# 发布说明

面向维护者的发布流程与验收清单。只做发布的人看这一份就够。

## 版本号规范（强制，由测试守着）

`main.go` 里的 `var Version` 是**唯一来源**，格式必须是 `X.Y.Z` 三段式，不带 `v` 前缀。
任何地方都不要另写生产版本字面量：

- 自动更新拿它和 GitHub 最新 release 的 `tag_name` 比较；
- 前端「关于」页读的是 `app.PSStatus.Version`（PS 版本）和这个 `Version`（程序版本）；
- 本地构建的 exe 文件名可以带版本号做区分，但正式 release 资产名不带版本号，版本靠 tag 区分。

`version_test.go` 把规范固化成测试，`go test ./...` 会拦下这三类错误：

| 测试 | 拦截的失误 |
|---|---|
| `TestVersionIsSemver` | `Version` 写成 `0.3`、`v0.3.16`、`0.3.16-beta` 等非法形态 |
| `TestChangelogHasCurrentVersionSection` | 改了 `Version` 却没在 `CHANGELOG.md` 新增同名 `## vX.Y.Z — YYYY-MM-DD` 小节 |
| `TestChangelogHeadingsAreOrdered` | 更新日志顺序乱、最新小节不等于当前 `Version`、同一版本重复 |

所以发版时这三步是一个整体，**顺序照下面走，中间不许跳过**：

1. 改 `main.go` 的 `var Version`（例如 `0.3.16` → `0.3.17`）
2. 在 `CHANGELOG.md` **最上方**（`# 更新日志` 头部说明之后、上一版小节之前）插入新小节：

   ```markdown
   ## v0.3.17 — 2026-11-20

   - 一条一句话说清用户能感知的变化。
   - 修复类写清"原来怎样、现在怎样"，不要写"优化了逻辑"。
   ```

   日期用**当天真实日期**，格式固定 `YYYY-MM-DD`；破折号用全角 `—`，前后各一个空格（测试按这个正则匹配）。
3. 跑 `go test ./... -count=1`，确认版本测试通过后再构建。

### 什么时候必须升版本号

- 改了任何会被用户感知的行为（套图判定、摆放策略、输出结构、界面文案）——必须升 `MINOR` 或 `PATCH`；
- 只改内部实现且行为完全不变（重构、注释、测试）——可以不升，但**不要**为了"顺手"改 `Version` 而不写日志；
- 只改 `CHANGELOG.md` 措辞不改版本——允许，测试不会失败。

### 反例（都会让 CI/本地测试红）

```text
✗ main.go: var Version = "0.3.17"   ← CHANGELOG.md 没有 v0.3.17 小节
✗ main.go: var Version = "0.3.17"   ← CHANGELOG.md 最新小节是 v0.3.16
✗ main.go: var Version = "0.3.14"   ← 构建出的 exe 界面显示旧版本，用户以为没更新
✗ CHANGELOG.md 把 v0.3.17 写在 v0.3.16 下面
```

最后一条尤其容易踩：**构建 exe 前必须确认 `Version` 已经改过**，否则快捷方式指向的新 exe 打开后标题栏还是旧版本号。

## 发布前验收清单

在仓库根目录依次跑，全绿才发：

```bash
go build ./...
go vet ./...
go test ./... -count=1
```

再手工确认三件事：

1. **能力矩阵**：`go run` 打印 `psx.For("27.7.0")`，`Verified` 必须是 `true`，
   `DoJavaScript` / `NoDialogs` / `EditSmartObject` 三项必须为 `true`，`ReplaceContents` 必须为 `false`。
2. **端到端**：`go run ./cmd/probe -config "<配置目录>" -pattern "<图案文件>" -template "<模板文件>" -out "<输出目录>"` 跑一次真实套图。
   它不经过 GUI，路径必须显式提供。确认退出状态为零，且 `OK <字节数> <路径>` 行数等于模板格数。
3. **前端**：`wails dev` 起来后逐页点一遍（套图 / 任务队列 / 成品 / 设置 / 关于），
   确认没有报错。**先走浏览器端口审查，最后才打包 exe**，不要靠反复操控桌面 GUI 验收。

## 打包

```bash
cd frontend && pnpm install && pnpm run build
cd .. && wails build -platform windows/amd64 -trimpath
```

产物：`build/bin/套图工作台.exe`（单文件，约 12MB）。

`build/bin/config.json` 是运行时生成的本地配置，**含用户 API Key，已在 `.gitignore` 里排除**，
不要手工加进仓库。

## 发布到 GitHub

走 `github-auto-publisher` skill 的两阶段流程，不要裸 `git push`：

```bash
python ~/.agents/skills/github-auto-publisher/scripts/publish.py plan \
  --repo . --remote origin --branch main \
  --message "release: vX.Y.Z" \
  --version-file main.go \
  --include main.go --include CHANGELOG.md \
  --check-json '["go","test","./...","-count=1"]'
```

`plan` 返回 `status: ready` 后再跑同一条命令的 `publish`。

skill 的硬性前提（踩过就知道多容易漏）：

- 本地 `git config user.name` 必须等于 `user.email` 里 `@users.noreply.github.com` 前的 GitHub handle；
- remote 必须是 github.com 的 **https** 地址；
- **远端分支必须已存在**，且远端 SHA == 本地 HEAD（首次建仓要先手动建立 main 基线）；
- `--version-file` 必须同时在 `--include` 里，且必须真的改了；
- 不能有 release hooks、不能是 detached HEAD、index 必须干净。

## 打 tag 与建 release

推送成功后：

```bash
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

把示例版本替换成 `main.go` 中的实际版本。推 tag 会自动触发 `.github/workflows/release.yml`：
先构建前端及 Go 编译、静态检查、测试，再用 Wails 打包，计算 SHA-256，并创建 Release 上传两个资产。
等待 CI 成功并核对 exe 与校验文件后才报告发布完成；构建失败时保留失败状态，修复后再发布。

## 自动更新怎么工作

用户在「设置」里勾上 `update_check`（默认开）时，程序启动后会：

1. `updater.CheckLatest(ctx)` 查 `https://api.github.com/repos/z2476720314-sys/titao-workbench/releases/latest`；
2. `updater.IsNewer(当前版本, tag_name)` 判断有没有更新；
3. 有则 `updater.Download` 下载 exe、`updater.VerifySHA256` 比对同 release 的 `.sha256` 附件；
4. `updater.ApplyReplace` 生成 `titao-update.bat` 并启动它，脚本等主进程退出后 `copy /y` 覆盖再拉起新版本。

**全程静默失败**：网络不通、被限流（403/429）、仓库 404、预发布/草稿，都只返回 error
不打断用户。`prerelease` 和 `draft` 永远不会被当作更新目标。

替换脚本不结束进程、不删用户数据，只重试 `copy /y` 最多 60 次（每次间隔约 1 秒）；
60 次仍失败就打印「更新失败：无法覆盖 …，请手动替换。」并 `pause`，不会把程序搞成打不开的状态。

## 版本兼容

`internal/psx/capability.go` 的 `For(version)` 按 PS 大版本判定能力：

| PS 大版本 | Verified | 说明 |
|---|---|---|
| 27（2025） | ✅ | 实测通过，本项目主目标 |
| 13–26 | — | 保守放行，标注「未实测」 |
| < 13（CS6 之前） | — | 缺 `placedLayerEditContents`，套图功能不可用，报错提示升级 |
| 未知 / 空 | — | 保守放行，标注「版本未知」 |

`ReplaceContents` 在任何版本都是 `false`。实测 `placedLayerReplaceContents` 会把智能对象
原有透视变换从 271×601 放大成 1331×3211，成品完全错位，所以本项目永远走
`placedLayerEditContents` 进内部文档替换这条路。
